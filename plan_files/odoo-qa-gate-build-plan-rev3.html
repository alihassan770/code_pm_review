01What this actually is

A gate, not a test runner. It takes a task and a commit, and returns a verdict with evidence. A test runner answers "did my tests pass". The question you actually have is "is this safe to show the client".

What changed in revision 3

Revision 2 still kept one escape hatch: where a diff was risky enough, it duplicated the client's staging database and ran a true twin comparison on the copy. On Odoo.sh, Cloudpepper, and the other managed platforms our clients actually run on, that is not available. There is one staging database, provided by the host, with no way to clone it, duplicate it, or stand up a second one. Revision 3 removes the escape hatch and everything that depended on it.

Two consequences follow, and they are the new material. The temporal baseline in section 8 is now the only baseline, with no true twin behind it, and three use cases become advisory rather than automated. And because there is exactly one database and people other than the gate need it, a run has to be able to stop, release the instance, and resume from where it left off. That is section 7, and it is the largest addition in this revision.

Out comes a verdict of pass regression unmet or inconclusive, plus an evidence bundle: an ordered screenshot walkthrough with a value ledger, a regression diff, a residue report accounting for anything the run left behind, and a one-paragraph summary written for a project manager rather than a developer.

Why testing in place is genuinely better

Your instinct here is right, and it is worth being explicit about what it buys, because it is more than convenience:

  • The real installed module set. A stack we assemble ourselves only ever contains the addons we knew to mount. A client's staging instance carries the third-party apps someone installed through the hosting panel, the theme module, the QuickBooks connector, the MUK web modules. Interaction bugs between your change and a module nobody remembered are a large share of what reaches clients, and they are invisible in a stack we assemble ourselves.
  • The real configuration. Their chart of accounts, their taxes, their fiscal positions, their warehouse routes, their pricelists, their Studio fields. A change that is correct against a clean install can be wrong against their tax configuration specifically.
  • No golden-database pipeline to build or keep fresh. That was two weeks of revision 1's roadmap and a permanent maintenance cost. It disappears.
  • The instance the client will actually accept on. Evidence screenshots come from the same URL the project manager and the client would open themselves.

What it costs, stated up front

Four things get harder, and the rest of this document is largely about handling them:

  1. Writing without altering existing data becomes the central engineering problem rather than a free consequence of throwing the database away. Section 5 and section 6.
  2. There is no twin, and now no way to make one. You cannot hold the same database at two code versions at once, and the host will not give you a second copy, so the baseline is temporal and that is the end of the matter. It costs precision, and three use cases with it. Section 8.
  3. The instance is shared with people. One database, one lock, and a developer who needs staging mid-run. A run must be suspendable and resumable or the team will route around it. Section 7.
  4. Safety is now an assertion about an instance we do not own rather than a network we control. This is the part where a mistake is an incident, so it comes first. Section 3.

02Seven load-bearing decisions

If any one of these is dropped the tool becomes a demo that gets abandoned. Four carry over from revision 1. Two came with in-place testing in revision 2. The seventh is new here, and it is what makes a single shared database workable rather than merely possible.

DECISION 1 · NEW

The regression suite runs inside a transaction that is rolled back

Scenarios execute in-process on the staging instance inside a savepoint, then roll back. Real data is read, written, asserted against, and released unchanged. This is the mechanism that makes "test on real data" and "do not affect existing data" both true at once, and it is the heart of the revision.

DECISION 2 · NEW

The instance opts in, or nothing runs

A staging instance must carry a hand-placed sentinel and pass a pre-flight safety audit before the gate will touch it. A production instance can never accidentally qualify. This is the single most important control in the design, because the failure it prevents is writing test data into a client's live system.

DECISION 3 · NEW

A run can be suspended and resumed

There is one database and it is shared with people. A run pauses at a checkpoint, releases the instance, and later resumes from where it stopped after re-auditing and re-fingerprinting the instance. Without this, one developer needing staging costs a whole run, and the team routes around the gate within a fortnight.

DECISION 4

Compare against a baseline, always

A result on its own cannot distinguish a new breakage from a pre-existing one, and unexplained failures get dismissed as noise. The baseline is now a nightly run rather than a parallel lane, with a data fingerprint attached so a stale comparison declares itself.

DECISION 5

Three execution tiers, matched to what may commit

Read-only probes, rolled-back transactions, and committed browser flows have completely different residue profiles and completely different coverage. Every scenario declares which tier it needs, and the tier decides what cleanup it owes. There is no fourth tier, because there is no second database to give it.

DECISION 6

Scenarios accumulate, they are not regenerated

AI proposes scenarios from the diff, a human ratifies them, they are committed to the client repo and run forever after. Regenerating tests every run gives flaky, unreviewable output and zero compounding value. This is what turns 40 untested client repos into tested ones.

DECISION 7

Test as several users, never only as admin

Access-rights regressions are among the most common in Odoo work and are completely invisible to an admin session. Every flow carries a persona list. Nearly free to implement, and it catches a whole failure class the manual process misses today.

03The instance contract

In revision 1, safety came from infrastructure we owned: an isolated network with no egress, a database we had just neutralized ourselves. None of that is available now, and on a managed host there is no second database to retreat to either. The gate is about to write to a live instance belonging to a client, so what replaces it has to be louder, stricter, and refuse by default.

Opt-in by sentinel

An instance becomes eligible only when a human deliberately marks it. The marker is a config parameter set by hand, once, on that instance:

ir.config_parameter
  key   = hst_qa.instance_role
  value = staging:<client_id>:<iso8601 timestamp>:<who set it>

The probe reads this before doing anything else. No sentinel, no run. The point is the direction of the default: an instance has to be walked up to and opted in, and there is no configuration mistake on our side that makes a production instance eligible. A wrong URL in a client config file then produces a refusal, not an incident.

The pre-flight audit · every one of these refuses the run
  1. Sentinel missing, malformed, or naming a different client than the run's client id.
  2. Database name not on the client's allowlist pattern. Configured per client, for example *_staging or staging_*. Belt to the sentinel's braces.
  3. Any active ir.cron record. A staging instance should not be running scheduled jobs, and crons firing mid-run both corrupt results and can act on rolled-back records.
  4. Any active ir.mail_server or fetchmail_server. This is the one that emails four thousand customers if you get it wrong.
  5. Any payment.provider not in test mode.
  6. A web.base.url that resolves to a production hostname, checked against the client's known production domain.
  7. Integration config parameters holding what look like live credentials, matched by key pattern against a per-client list of the endpoints that module set touches.
  8. A module declaring an outbound integration with no stub registered for it. See the convention below.

The audit result is recorded in the bundle with every check and its outcome, so a refusal is self-explanatory and a pass is auditable after the fact. Re-audited at the start of every run, never cached, because a client's hosting provider can re-enable crons or mail during a platform update without telling anyone.

Guards inside the run, as defence in depth

The audit proves the instance's resting state. It cannot prove what your code does once it executes, so the probe additionally patches, for the duration of each QA transaction only:

PatchedBehaviour during a QA transactionWhy
IrMailServer.connect and send_emailRaises, and the attempt is recorded as a findingCatches code that sends mail inline rather than queueing it for cron
requests.Session.requestRaises unless the target matches a registered stubCatches outbound integration calls. An unstubbed call is a finding, not a silent success
Cursor.commitRaisesAn explicit commit would escape the rollback. It is also a code smell worth reporting on its own
Cursor.execute on DDLRaisesSchema changes do not belong inside a scenario, and some do not roll back cleanly
The convention worth establishing before any of this is built

Every custom module that talks to the outside world declares it in its manifest and ships a stub descriptor. The gate refuses to run a scenario touching a module that declares an integration without one. That converts a recurring human check into a structural one, and it is the highest-value convention to adopt early. The QuickBooks connector, the ZK attendance sync, and the ESC/POS printer bridges are exactly the modules that need it.

Per-client capability flags

Access to client hosting is not uniform, and on managed platforms it is deliberately restricted: Odoo.sh and Cloudpepper hand you a web console and an RPC endpoint, not a shell and not a database. So the design's floor is authenticated JSON-RPC and nothing else, which is precisely why the probe module exists rather than a collection of shell scripts. Everything the gate needs to be correct sits on that floor. The one capability above it is a convenience, and no use case depends on it:

CapabilityChannelUnlocks
rpcHTTPS JSON-RPC with an Odoo API keyEverything in tiers 1 to 3. The baseline. Assumed present for every client
browserHTTPS to the same host from PlaywrightThe evidence plane. Present wherever RPC is
shellSSH, PEM key or Tailscale. Absent on most managed platformsServer log retrieval for tracebacks, module upgrade without the hosting panel, asset rebuild. Convenience, never capability

There is no db capability, and this is the defining constraint of revision 3. Odoo.sh, Cloudpepper, and the managed hosts our clients run on do not hand out a Postgres superuser connection, and none of them will let you CREATE DATABASE from a copy of the staging one. Revision 2 assumed that access existed for a minority of clients and built an escalation path on it. That path is removed rather than made optional, because a feature available to three clients out of forty is a feature nobody builds scenarios against.

The upshot is a simpler and more honest promise: every client gets exactly the same gate. There is no tier of client that gets better answers, and nothing in the roadmap is gated behind hosting access somebody has to negotiate. What is lost, stated plainly rather than buried in section 18, is module uninstall testing, migration script verification, and version upgrade dry runs. Section 18 covers what replaces them.

04Architecture

Two processes we run, plus a small module installed on each client staging instance. There is no container orchestration, no database provisioning, and no infrastructure of ours between the runner and the client's instance. Everything the gate does, it does over the network to a host somebody else operates.

ComponentLanguageRuns onResponsibility
Control plane
api/		 TypeScript, Express Railway, next to the PMO dashboard Run queue with a per-client lock, run history, Odoo task read and chatter write, report hosting, auth
Runner
runner/		 Python 3.12 One host, ours Claims jobs, parses diffs, deploys the branch to staging, calls the probe, drives Playwright, assembles the bundle
Probe module
hst_qa_probe		 Python, an Odoo module Installed on each client staging instance Runs scenarios in-process inside a rolled-back savepoint, enforces the guards, reports the pre-flight audit, records the creation registry

The runner does not need to be co-located with anything, because there is nothing local for it to reach: no container socket, no database to copy, no per-client infrastructure. It holds credentials and speaks HTTPS. One modest host serves every client, and adding a client is a config entry rather than a provisioning job.

One run at a time, per client

This is the throughput consequence and it needs stating plainly. A client has one staging instance, and a run needs that instance to be running one specific commit. So runs serialize per client. The control plane holds a per-client lock and queues behind it.

In practice this is fine: a run is 12 to 20 minutes, so a client absorbs around 20 runs a day, well above what five developers generate against a single client. But it does mean a run cannot start while a developer is manually clicking through the same staging instance, and the lock has to be visible in the dashboard so people can see why they are waiting.

Waiting is only acceptable if it is bounded, and on a single shared database it is not bounded by default: a run that has to finish before anyone else can work is a run people will kill. So the lock is surrenderable. A run pauses at a checkpoint, hands the instance over, and resumes later without losing what it had already proved. That mechanism is section 7, and it is the reason one instance per client is a constraint rather than a bottleneck.

A prerequisite in odoo-dev-loop worth changing first

odoo-dev-loop's client config defaults to branch_mode: "shared", where every task lives on one working branch. If two tasks are sitting on that branch together, the gate deploys both at once and a regression cannot be attributed to a task. The verdict would be correct and useless.

branch_mode: "per_task" is effectively a prerequisite for clean attribution, so switch clients over as they come onto the gate. Where a client has to stay on shared, the gate can still run, but its findings must be reported against the branch rather than the task, and that is worth knowing before someone argues about whose change broke it.

05The probe and rollback

This section is the mechanism the whole revision rests on. Everything else is plumbing around it.

Why it has to be in-process

Over JSON-RPC, every call is its own transaction and commits when it returns. There is no way to begin a transaction, make twelve calls, and roll back, because the first call has already committed. So a scenario cannot be a sequence of RPC calls if it is going to be undone.

Instead the scenario travels as data in a single RPC call, and executes inside the Odoo process where one transaction spans the whole thing. That transaction is wrapped in a savepoint which is unconditionally rolled back. Odoo's own test framework has worked this way forever, with TransactionCase doing exactly this against a real database. The probe is that idea, reachable remotely.

# hst_qa_probe/models/probe.py  (shape, not final code)

class _Rollback(Exception):
    """Sentinel. Never escapes run_scenario."""

class QaProbe(models.AbstractModel):
    _name = "hst.qa.probe"

    @api.model
    def run_scenario(self, spec):
        self._assert_sentinel()          # refuse if not opted in
        results, log = [], []

        self.env.flush_all()             # nothing pending leaks into the savepoint
        try:
            with self.env.cr.savepoint():
                with self._guards(log):  # mail, http, commit, DDL
                    results = self._execute(spec)
                raise _Rollback()
        except _Rollback:
            pass
        finally:
            self.env.invalidate_all()    # the cache still holds rolled-back values

        return {"results": results, "guard_events": log}

Two lines there are easy to leave out and both cause real bugs. flush_all() before the savepoint, or pending ORM writes from earlier in the request get swept into it. And invalidate_all() after the rollback, or the environment cache keeps serving values that no longer exist in the database, which produces assertion results that are confidently wrong.

What rollback does not undo

Rollback is close to complete, not complete. These are the leaks, and each needs a decision rather than a hope:

LeakWhyHandling
Postgres sequences ir.sequence with the standard implementation uses a real Postgres sequence, and nextval is deliberately non-transactional. Confirming an order consumes its number whether or not you roll back Numbering gaps on a staging instance are harmless, so the default is to accept them and record which sequences were touched. Optionally the probe captures last_value before and restores it after, which is safe on staging because concurrency is low but is not safe in general
Explicit commits in the code under test Any cr.commit() ends the transaction and makes everything before it permanent The guard patches commit to raise. The scenario fails with a clear message, and the commit itself is reported as a finding, because inline commits in business logic are a defect worth fixing
Filestore writes ir.attachment writes its file to disk before the transaction ends The database row rolls back, leaving an orphan file that Odoo's own attachment garbage collection removes. No action needed beyond knowing why the filestore grows slightly
Anything outside Postgres Emails, webhooks, external APIs, printed documents Not a rollback problem at all. Handled by the pre-flight audit and the in-transaction guards in section 3, which is why those are not optional
Lock contention A transaction that writes a hot row holds a lock until it rolls back, which can block a person using staging at that moment One scenario per transaction, so transactions last seconds. lock_timeout and statement_timeout set on the probe's work so it fails fast rather than blocking a human, and a timeout reports as inconclusive rather than as a failure

The honest summary: for ORM-level business logic, which is the overwhelming majority of what your custom modules do, rollback isolation is effectively complete. The leaks are enumerable, each is either harmless or reported, and none of them modify existing client records.

The creation registry, for what cannot roll back

Tier 3 flows drive the browser, so they commit, and they need a different mechanism. During a committed run the probe hooks create across all models and records every (model, id) it produces, along with the ordering.

That registry is a reliable ledger of everything the run made, which name prefixes and marker tags are not. Cleanup walks it in reverse creation order. Where unlink is refused, and Odoo refuses plenty, the probe applies the documented reversal for that model and, failing that, reports the record as residue with its id and the reason. Section 6 covers what that means in practice, and section 14 covers how it appears in the bundle.

06Isolation tiers

Every scenario declares one tier. The tier decides what the scenario may do, what it can verify, and what cleanup it owes. Coverage rises down the list and so does residue, which is the whole trade.

Tier 1
read-only

Probes that never write

View resolution and arch validation across every inheriting view, report rendering against existing records, ACL and record-rule evaluation per persona, query-count measurement, search and read performance on real data volumes.

Residue none Cost seconds Misses anything requiring state change
Tier 2
rollback

Write, assert, roll back

The regression suite lives here, and it is where most of the value is. Full business flows over the ORM: create, confirm, deliver, invoice, pay, cancel, reverse. Constraint and compute behaviour on real data. The persona matrix. Everything in section 5.

Residue sequence numbers only Cost 0.5 to 3s per scenario Misses everything visual, and anything spanning multiple HTTP requests
Tier 3
committed

The evidence plane. Playwright drives the real web client, so every click commits. This is the only tier that produces screenshots, and the only one that catches view rendering, OWL errors, and widget behaviour. 4 to 10 flows per run, not a regression suite.

Residue bounded, reversed, and reported Cost 30 to 120s per flow Misses nothing visual, but too slow and flaky to run broadly
There is no tier 4

Revision 2 had one: duplicate the staging database, run a true twin comparison or a destructive test on the copy, drop it. On a managed host there is no copy to be had, so the tier is gone rather than optional.

What it took with it: module uninstall testing, migration script verification, and version upgrade dry runs. Those are not merely slower now, they are outside what the gate can do, and sections 10 and 18 say so where a reader would otherwise assume coverage. Pretending a temporal comparison substitutes for a twin would be the more comfortable choice and the wrong one.

Tier 3 is where "do not affect existing data" needs care

Tiers 1 and 2 satisfy the constraint outright. Tier 3 cannot, because a browser click is a committed transaction, and there is no mechanism that undoes it invisibly. So the goal shifts from zero residue to bounded, reversed, and accounted-for residue, with three rules:

  1. Nothing existing is ever modified. Tier 3 flows may only create new records and act on records they created. A flow that needs to edit an existing customer order creates its own order instead. The registry makes this enforceable rather than aspirational: any write to a record id not in the registry aborts the flow.
  2. Cleanup runs in reverse, and reports what it could not do. Draft records unlink cleanly. Confirmed orders cancel then unlink. Posted journal entries cannot be deleted at all, only reversed, so they are reversed and both entries are reported as residue. Done stock moves are the same story. This is Odoo behaving correctly, and pretending otherwise would be the mistake.
  3. Residue is visible in the bundle, per record, with model, id, and why it survived. Never silent. A project manager reading the report can see exactly what the run added to staging, and a scheduled sweep reconciles the registry against the instance weekly to catch anything cleanup missed.
The optional stronger answer, per client

For clients whose staging books must stay pristine, tier 3 can run inside a dedicated QA company in the same database: its own journals, warehouse, and sequences, with a QA user who can only see it. Odoo's own multi-company record rules then do the isolation, and posted entries never touch the client's books at all.

The trade is real and worth understanding before choosing it. A QA company is not the client's company, so you are no longer testing against their exact journal, tax, and warehouse configuration, which was one of the main reasons to test in place. It also needs per-client setup, and on a single-company client it means enabling multi-company, which some custom modules handle badly.

Recommendation: default to the client's real company with registry cleanup, and reach for a QA company only for accounting-heavy clients or where someone objects to reversal entries appearing on staging.

07Pausing and resuming a run

There is exactly one staging instance per client and people other than the gate need it. Section 4's per-client lock is what makes runs correct, and it is also what makes them obstructive: without a way out, a developer who needs staging must either wait out a twenty-minute run or kill it and lose everything it had already proved.

So a run is not a single indivisible operation. It is a sequence of checkpointed units that can be suspended between any two of them, releasing the instance, and picked up later from the last checkpoint rather than from the beginning. This section is new in revision 3, and it is the direct consequence of never having a second database to fall back on.

What pausing actually releases

Two different things get asked for when somebody says they need staging, and conflating them produces a feature that does not help:

ModeWhat it doesCost to resumeWhen
release Drops the per-client lock and stops executing. The task branch stays deployed. The instance is free to use, running the code under test Seconds. Re-acquire the lock and carry on The default. Usually the person asking for staging wants to look at this task's work anyway, which is already deployed
yield Drops the lock and redeploys the branch the instance carried before the run started, restoring it to its resting state Two to four minutes, because the task branch has to be deployed again Somebody needs staging for unrelated work, or for a different task's branch

Both are real pauses: results already collected are kept, and the run resumes from its checkpoint. The difference is only what state the instance is left in, and the bundle records which mode was used so a reader knows what the instance looked like during the gap.

Where a run may pause, by tier

A pause request does not interrupt work in flight. It is honoured at the next checkpoint boundary, and what that boundary costs differs sharply by tier, which is the reason section 6's tiers had to be explained first.

TierCheckpoint boundaryWorst-case waitWhat is at risk
Tier 1
read-only		 Between probes Under a second Nothing. Probes write nothing, so a pause is free and a repeat is harmless
Tier 2
rollback		 Between scenarios, on the rollback that already ends each one Around 3 seconds Nothing. The transaction boundary is the checkpoint boundary, which is the single luckiest thing about this design
Tier 3
committed		 Between flows, never inside one Up to 120 seconds Real. A flow interrupted halfway has created records and not yet cleaned them up. See below

Tiers 1 and 2 get this almost for free. Every scenario is already a self-contained call that ends in a rollback, so "stop after this one" needs a flag check between calls and nothing else. The checkpoint is the list of scenario ids that have completed and their results.

Tier 3, where pausing costs something

A browser flow commits as it goes, so an interrupted flow leaves records behind that its own cleanup step has not reached yet. Three rules, in the same spirit as section 6:

  1. A pause request never lands mid-flow. The current flow runs to completion, including its cleanup, and the pause is honoured after. A flow is 30 to 120 seconds, so the wait is bounded and predictable, and the operator is shown the estimate when they click.
  2. An abort is different from a pause, and is offered separately. Where somebody needs the instance immediately, the flow is abandoned and the creation registry is walked in reverse right then. That reclaims the instance in seconds rather than minutes, at the cost of re-running the whole flow on resume rather than skipping it.
  3. A paused run reports its interim residue. Records created by completed flows are already cleaned; what remains is whatever the tier's normal reversal rules could not remove. The pause writes a partial residue.json so the instance's state during the gap is documented rather than assumed, and a paused run that is never resumed is swept by the weekly reconciliation the same as any other.

The checkpoint

Written to the control plane after every completed unit, not held in the runner's memory, so a runner crash or a machine reboot is recoverable in exactly the same way an operator pause is:

{
  "run_id":        "run-8421",
  "phase":         "tier2",
  "completed":     ["sale.line_discount", "mrp.unbuild_finished_order", ...],
  "results":       [...],              # everything asserted so far
  "plan_sha":      sha256 of plan.json,  # the plan may not change under a resume
  "head_sha":      the commit that was deployed when work started,
  "pre_pause_ref": the branch to restore under `yield`,
  "fingerprint":   the instance fingerprint at the moment of the pause,
  "registry":      tier 3 creation registry, with cleanup state per record,
  "paused_at":     timestamp,
  "expires_at":    timestamp + the client's resume window
}

The plan_sha is worth more than it looks. A resumed run must execute the plan that was approved before the pause, not a freshly generated one. If the task description changed in the gap, that is a new run rather than a continuation of this one, and the checkpoint refusing to match is what makes that automatic rather than a matter of somebody noticing.

What resume checks, and what happens when a check fails

Gate 3 is the interesting one, because it reuses the fingerprint machinery from section 8 with no new mechanism at all. The comparison is between the fingerprint taken at the pause and the one taken at the resume, and the response is graded rather than binary:

What moved during the pauseResponse on resume
Nothing. Fingerprints matchResume from the checkpoint. The normal case, and the only one that is silent
Row counts moved within toleranceResume, noted in the bundle. Somebody used staging, which is exactly what the pause was for
A different branch was deployed and left thereRedeploy head, then resume. Results already collected still stand, because they were collected against head
Module set or config changedCompleted results are marked suspect rather than discarded. Scenarios whose blast radius touches the changed module are re-run; the rest are kept. This is the graded response that makes a long pause survivable
The pre-flight audit now failsVerdict instance unsafe, exactly as at the start of a run. No blame, lead alerted, nothing further written
The checkpoint is past expires_atResults are advisory only and the run restarts. Default window 24 hours, per client
plan_sha no longer matches the taskRefuse to resume. The task changed, so this is a new run
Why partial invalidation rather than starting over

The tempting simplification is to throw the checkpoint away whenever anything moved. It is also the one that makes the feature useless: an overnight pause on a busy client almost always sees something move, so a strict rule means every long pause costs a full re-run and people stop pausing.

Re-running only the scenarios whose blast radius intersects what changed is the same selection logic section 10 already performs against a diff, pointed at a fingerprint delta instead. No new machinery, and it keeps the common case cheap.

Who can pause, and the request queue

Three ways a run pauses, and the third is the one that makes this a feature rather than a control:

  • An operator clicks pause in the dashboard, choosing release or yield. The estimated wait to the next checkpoint is shown before they commit to it.
  • The runner pauses itself on a lock timeout, a deploy failure, or an instance that stops answering. That is a pause rather than an inconclusive verdict, because the work already done is worth keeping and the cause is often transient.
  • Somebody requests the instance. A developer clicks "I need staging" on the client's page rather than hunting down whoever started the run. The request is queued, the run pauses at its next checkpoint, and the requester is notified when the instance is theirs. This is what replaces the current practice of messaging the team and hoping.

A paused run holds its place in the queue, so resuming does not mean starting again behind three other clients' work. Section 4's lock is unchanged: still one run at a time per client, still visible in the dashboard, now with a legitimate way to hand the instance over mid-run.

Additions to the contract

08Baseline without a snapshot

Revision 1 ran base and head lanes side by side on identical database clones, which made "this scenario passed before your change and fails after it" airtight. Revision 2 kept that as an escalation for high-risk diffs. Revision 3 has neither, because the host will not give us a second database, so the airtightness has to be replaced with something weaker and honest about being weaker.

The fingerprint

Cheap to compute over RPC, and it is what turns a silent trust assumption into an explicit check:

{
  "modules":  sha256 of (name, installed_version, state) for every installed module,
  "config":   sha256 of ir_config_parameter keys and values, excluding our own,
  "views":    count of ir_ui_view + max write_date,
  "volumes":  row counts for the models in the blast radius, with a tolerance band,
  "sentinel": the opt-in value, so a re-opt-in is visible,
  "taken_at": timestamp
}

The modules hash is the important one. It catches somebody installing an app through the hosting panel between the baseline and the candidate, which is otherwise an invisible cause of a mysterious new failure.

Scenarios must be drift-immune to be comparable

Because the data underneath moves, scenario authoring gains one hard rule and one classification:

  • Build your own fixtures. A tier 2 scenario creates the records it needs inside its transaction rather than asserting on the state of existing ones. Resolving "any customer with a sales history" by query is fine. Asserting that customer S00312 has a total of 4,120.50 is not, because someone will edit it on staging next Tuesday.
  • Data-dependent scenarios are tagged and treated differently. Some checks are genuinely about existing data: how many records have a NULL in the new stored field, does the report render for the client's five weirdest historical orders. Those are valuable and they are inherently drift-sensitive, so they are compared only within a single run window, never against last night's baseline.

This rule was good practice in revision 1 and is a requirement now. It is worth enforcing in the scenario schema rather than in review comments.

When the baseline is stale, and what to do

SituationResponse
Fingerprint matchesComparison stands. Normal case, most of the time

Diff carries a high risk signalTake a fresh baseline immediately before deploying head, rather than relying on last night's. It costs the suite's runtime twice but removes most of the drift window, and it is the closest thing to a twin that a single database allows

The tightest baseline a single database permits

Worth naming, because it is the mitigation that replaces tier 4. For a high-risk diff, run the selected suite against the current staging code first, deploy head, then run it again. Both halves see the same database minutes apart rather than hours, and no third party has touched it in between because the gate holds the lock across both.

That is not a twin: the two halves still run at different moments, and a cron or a colleague could in principle intervene. But it collapses the drift window from overnight to minutes, it needs no hosting access at all, and it costs one extra suite runtime on the small fraction of diffs that warrant it.

09The client knowledge base

The impact graph in the next section is only as good as its answer to one question: what else is installed on this client's instance, and what does it touch? Getting that answer wrong is how a change ships having been tested only against the module it lives in.

The mistake to avoid is treating this as a document somebody maintains. It is four layers with four different lifecycles, and only one of them involves a human writing anything.

What already exists, and its two gaps

odoo-dev-loop already carries a per-client knowledge base at state/knowledge/<client_id>.json. It holds manifest metadata per module, each module's CLAUDE.md verbatim, regex-extracted _name and _inherit declarations plus field definitions, and free-form user notes. code_review.py consumes it through render_for_prompt, which is already well built: it renders detail blocks for the modules intersecting the diff and a brief index for everything else, capped at 30 KB.

Its header says it is deliberately not a vector database, not LLM summaries, and not a file watcher. That restraint was the right call and it should survive this. Two things do need fixing:

  • It knows the repository, not the instance. It has no idea which third-party modules are installed, which Studio fields exist, or which module patches which view. That is exactly the context the gate needs, and it is precisely what testing in place makes available.
  • Extraction is regex, and staleness is flagged rather than repaired. is_stale compares the repo HEAD against repo_sha_at_build, and the poller deliberately does not auto-update. For a review prompt, a missed _inherit costs some quality. For deciding a blast radius it means an untested flow, which is a different order of problem.

Layer 1: Odoo's own metadata is the knowledge base

This is the part worth internalising, because it removes most of the guesswork. ir.model.data attributes every field, view, ACL, rule, and action to the module that created it. So over plain authenticated RPC, with no source access and no shell, the gate can derive:

  • The installed module set with versions and authors, and which of those we hold source for
  • Every field on a model and which module added it, including whether it is stored, computed, or related
  • View inheritance chains with per-node module ownership, so you can see who patches whose xpath and in what order
  • ACLs and record rules, per module
  • Studio customizations: fields with state = 'manual', and records owned by the studio_customization module. This is the set that exists in no repository at all, and it is invisible to any repo-based analysis
  • Server actions, automation rules, and crons, per module
# attribute every field on the blast-radius models to its owning module
fields = env['ir.model.fields'].search_read(
    [('model', 'in', models)],
    ['name', 'model', 'ttype', 'store', 'compute', 'related', 'state'])

owners = env['ir.model.data'].search_read(
    [('model', '=', 'ir.model.fields'),
     ('res_id', 'in', [f['id'] for f in fields])],
    ['module', 'res_id'])
# -> field id -> owning module, for every field, including third-party ones

ir.model.data is the path that behaves identically across 17, 18, and 19, which is why the census uses it rather than the convenience columns some versions add. The whole census is a handful of search_read calls and takes seconds, which is what makes rebuilding it per run affordable.

The consequence is that you never have to guess what a third-party module does to a model you are changing. If the Emipro theme patches the sale order form, the instance says so. If muk_web_chatter overrides a view in your change's inheritance chain, the instance says so, and it says so for the client where it is actually installed rather than for all of them.

The honest limit of metadata, and the fallback

Metadata tells you what a module declares, not what its Python does. A third-party module that overrides write() in a way that breaks your computed field leaves no trace in ir.model.data.

Where we hold the source, layer 2 covers it. Where we do not, there are two fallbacks, in order: read the module's source off the instance filesystem when the client has the shell capability, and otherwise treat unknown-source modules as high-risk consumers whose flows are always selected rather than reasoned about. When you cannot analyse it, test it. That is a worse outcome than analysis but a much better one than assuming it is inert.

Layer 2: the source map replaces the regex extractor

The impact engine already needs a real AST parse in phase 0. That parser produces a strict superset of what the existing regex extractor produces, so the two consolidate: one extractor, the same JSON shape, richer content. Method overrides and whether they call super(), @api.depends chains, @api.constrains, raw SQL, sudo() use, and outbound HTTP imports all become available.

Worth noting that this improves code review as a side effect, not just the gate. render_for_prompt keeps its focus-file scoping and its 30 KB cap and simply has better facts to render, so the reviewer prompt gets more accurate at no extra cost.

Layer 3: the curated overlay

What cannot be derived from anywhere: business invariants, regulatory constraints, the reason a module is fragile, which apps the client does not use. It lives in the client's own repo at qa/knowledge.yml next to their scenarios, changes by pull request, and is small by design.

Four mechanisms, none of which is "remember to keep it up to date":

Layer 4: regression memory

Append-only, written by the gate itself, and the layer that makes the knowledge base get smarter rather than merely larger.

Every confirmed regression stores the signal fingerprint of the diff that caused it, the scenario that caught it, the model and method involved, and the fix. When a later diff's signals resemble a stored fingerprint, those scenarios are force-selected even if the blast radius would not have reached them.

signal:   mrp.production :: write override
caught:   mrp.unbuild_finished_order
symptom:  ValueError: Expected singleton
fix:      override iterated records instead of assuming one
recorded: 2026-08-31, run-8421, task 4471
→ any future write override on mrp.production auto-selects the unbuild scenarios

This targets the way Odoo failures actually cluster, which is by model and method rather than by feature. It costs nothing to store, and after twenty or thirty regressions it is selecting scenarios that no static analysis of the diff would have justified.

The same layer accumulates learned cleanup rules: which models refused unlink in which state, and which reversal worked. So the tier 3 cleanup walker gets better per client over time without anyone writing rules by hand, and residue trends down as a consequence of running rather than as a separate project.

10Blast radius analysis

You asked for "all possible scenarios". That set is infinite, and a tool that chases it produces a suite so slow and flaky the team routes around it. The workable version is risk-based selection: read the diff, work out what it can possibly have broken, and test that exhaustively.

The runner parses changed files into signals, maps signals to affected models, maps models to the flows that touch them, and emits a bounded work list with a tier assigned to each item. Python goes through the standard library ast module, XML through lxml. No regex over source.

11The test plan

The gate selects work mechanically and proposes scenarios with a language model. Neither is visible unless you deliberately make it visible. The test plan is the artifact that puts both in plain language, in front of a human, before the run executes.

It answers three questions a reviewer actually has. What did you understand the task to be. What workflow will you walk through. What exactly are you going to test, and why that.

Reading the task properly

The task description is the primary input, and real ones are messier than the convention in section 14 assumes. So the interpreter reads more than one field:

SourceWhy it is read
descriptionThe main requirement. An HTML field, so it needs converting to text with list structure and line numbering preserved, because citations point at lines
The acceptance fenced blockMachine-readable criteria where the convention has been followed. Its absence is itself worth reporting
Chatter, mail.message on the taskRequirements arrive as follow-up comments constantly. A plan built only from the description will miss the clarification the project manager posted three days later, which is exactly the requirement the client cares about
AttachmentsNamed and listed. Where the AI layer has a vision-capable model configured, screenshots and mockups are read too. Where it does not, an attachment-only specification is reported as a gap rather than guessed at
allocated_hours, stage, assigneeContext and scale. A 2-hour task with a 40-step interpretation means the interpretation is wrong

Two practical notes from your task corpus. Descriptions mix languages, so the interpreter must restate in English without silently dropping content it did not parse. And a description that amounts to "see the attached email" must produce a plan that says insufficient specification loudly rather than inventing a plausible requirement, because a confident interpretation of a task nobody actually specified is worse than no plan at all.

Provenance on every step, which is the whole point

A reviewer scanning a plan needs to know instantly which steps are machine-selected and safe to skim, and which are model judgment and worth reading closely. So every test step carries a from tag:

That single column is what makes the plan a five-minute read rather than a full audit. In a typical run, two or three steps carry desc: or ai:new and the other eighty are mechanical.

When a bounced task comes back, the plan is regenerated and diffed against the previous one. A reviewer who already read the first plan then reads three lines instead of forty:

Run the interpreter at assignment time as well

The same component has a second, arguably higher-value placement. Run parts 1, 2, and 4 when a task is assigned, before any code is written, and post them to the task.

A developer then starts from a restated requirement and an explicit ambiguity list. AMB-01 gets resolved before three days of work is built on the wrong threshold, rather than after. Nothing about the implementation is needed to produce it, since parts 1, 2, and 4 come from the task text alone, so this costs one extra AI call at assignment and no infrastructure.

It also improves the tasks themselves over time. A team that sees its own descriptions restated back at it, with the ambiguities listed, writes better descriptions within a month. That is a real side effect and it is worth having even if the gate is never enabled for blocking.

What the plan deliberately does not do

Selection stays deterministic. The impact graph picks the scenarios, and the model writes prose about them, proposes new ones for ratification, and restates the task. It does not choose what runs, and the plan never influences the verdict.

The distinction shows up in the from column, which is why that column is not decoration. Every step is either traceable to a mechanical rule, to a line of the task, or to a proposal explicitly marked as needing a human. There is no fourth category, and if a step ever appears without provenance that is a bug in the generator.

12The scenario format

One YAML file per scenario, declarative, checked into the client repo under qa/scenarios/. The same file drives either the rollback tier or the browser tier, which is the point: a business flow is described once, run fast and reversibly in the regression suite, and re-run in the browser when it needs to produce screenshots.

qa/scenarios/sale/line_discount.yml

id: sale.line_discount
title: A line discount reduces the order total and carries to the invoice
tags: [sale, regression, ratified]
versions: ["17.0", "18.0", "19.0"]
personas: [sales_user, sales_manager]
tier: 2                    # rollback. required key, no default
drift: immune              # immune | data_dependent
covers: [AC1, AC2]

fixtures:                  # created inside the transaction, never reused
  partner:  {model: res.partner, pick: {customer_rank: {">": 0}}, limit: 1}
  product:  {model: product.product, new: {name: "QA-{run} Widget",
             list_price: 100.0, type: consu, taxes_id: []}}

steps:
  - create:
      model: sale.order
      values:
        partner_id: $partner
        order_line: [[0, 0, {product_id: $product, product_uom_qty: 10}]]
      as: order
  - assert: {expr: "$order.amount_total", equals: 1000.0}
  - write:  {on: "$order.order_line[0]", values: {discount: 10.0}}
  - assert: {expr: "$order.amount_total", equals: 900.0, because: "10% off 1000"}
  - call:   {on: $order, method: action_confirm}
  - assert: {expr: "$order.state", equals: sale}
  - call:   {on: $order, method: _create_invoices, as: invoice}
  - assert: {expr: "$invoice.amount_untaxed", equals: 900.0}
  - assert.no_traceback: true

The whole file travels as one run_scenario call and comes back rolled back. An evidence scenario is the same grammar at tier 3, with UI verbs and explicit capture points. Selectors are logical, written as @field:name or @button:method, and resolved to real CSS by the version adapter, which is what stops a v19 upgrade from invalidating every scenario you own.

id: sale.line_discount_evidence
extends: sale.line_discount        # inherits fixtures and assertions

Four details that matter more than they look

tier is required and has no default

An author has to state what the scenario may do to the instance. There is no accidental path to committing on a client's staging database, and reviewing a scenario means reviewing its residue profile. This is the schema-level expression of the whole revision.

readback, not just input

After every save the runner reads the fields back out over RPC and records both what was typed and what the database ended up holding. Odoo onchange handlers routinely change a value after you enter it, and a screenshot alone cannot distinguish "the user typed 900" from "the system computed 900". The readback column is what makes the evidence bundle actually evidential.

because, on every assertion

The optional because string is what appears in the report when the assertion fails. Without it a reviewer gets expected 900.0, got 1000.0 and has to go read the YAML. With it they get a sentence. Make it required in review even though the schema allows omitting it.

No wall-clock dependence

Scenarios never assert on "today". A run pins TZ, and a scenario needing a date uses an explicit as_of value carried into the Odoo context. A scenario asserting on today's date passes for a month and then fails on the first of the next one, and that single class of flake will cost you the team's trust faster than anything else here.

The summary paragraph

One AI-written paragraph at the top, for a reader who will not scroll. Generated from verdict.json and the task description, constrained hard: state the verdict, state what was demonstrated, state what broke, name no file paths. Uses the PMO dashboard's existing multi-provider AI layer with its fallback chain, so it costs nothing new to operate.

Keep the AI out of the verdict

The verdict is computed from assertion results and the baseline diff, deterministically. The AI writes prose about a decision already made, and proposes scenarios a human ratifies. It never decides pass or fail, and it never decides whether an instance is safe to touch. The moment a language model sits in the decision path, every argument about a result becomes unresolvable and the gate stops being a gate.

Coverage of acceptance criteria

unmet needs the task's acceptance criteria to be machine-readable, which means a small convention in how tasks are written. In the Odoo task description, criteria go in a fenced block:

```acceptance
- AC1: A line discount percentage reduces the order total
- AC2: The discount carries to the generated invoice
- AC3: Only Sales Managers may enter a discount above 20%
```

Each ratified scenario declares which criteria it covers via covers: [AC1, AC2]. Any criterion with no passing assertion is unmet. This convention is worth adopting whether or not the gate ever gets built, and AC3 there is exactly the kind of criterion only a persona matrix can verify.

Do not turn the gate on as a blocker on day one

Run it in advisory mode for the first four to six weeks: it produces bundles and comments on tasks, and blocks nothing. Use that window to measure the false-positive rate per client. Enable blocking per client only once its suite has been green across ten consecutive unrelated tasks.

In this revision there is a second reason to wait, beyond credibility. Advisory mode is also how you find out which client staging instances are actually neutralized, which have crons quietly running, and which have a live mail server nobody remembered. Expect that audit to fail on more instances than you would guess, and expect fixing those to be genuinely useful work in its own right.

Bringing up a new version

This is the process that decides whether the tool is alive in three years, so make it a documented drill rather than an improvisation:

  1. Copy the previous profile and bump it. Run the flow library against a vanilla Odoo install of the new version, locally, with demo data. Nothing client-specific yet, and no client instance involved.
  2. Every failure is either a selector to remap or a genuine flow change. Fix the profile until the library is green. Budget two to four days, mostly selectors.
  3. Point it at the first client staging instance running the new version. Failures here are the real upgrade findings, and this step is itself a saleable service. See UC-08.

Note that step 1 still uses a local throwaway Odoo. Testing in place is the right model for verifying client work, and the wrong model for developing the gate itself. Keep a plain local Odoo checkout per version, each with its own virtualenv and its own throwaway database, as the gate's own development fixture. No containers are needed for this and none should be introduced: the fixture exists so the flow library can be exercised against a vanilla install, and a source checkout does that with less machinery than anything else.

17End-to-end walkthrough

A real-shaped task, from the developer finishing it to the project manager reading the verdict. Timings are the target budget, not a guess after the fact: the run has to land inside 20 minutes or developers stop waiting for it and start ignoring it.

The task

Client: Legacy Maker Meats  ·  Odoo 18  ·  Module: hst_mo_carcass_weight  ·  Hosting: Cloudpepper  ·  Capabilities: rpc browser shell

Capture a secondary carcass weight in kilograms alongside the existing pounds field on the manufacturing order, show both on the kill sheet report, and require a Production Manager to approve when the two disagree by more than 2 percent.

  1. Developer finishes and pushesT+0

    Work happens as it does today, inside odoo-dev-loop. The developer hits Run code review, the local AI review passes, and they push their task branch. This client is on branch_mode: per_task, so the branch carries only this task.

  2. Gate enqueued, per-client lock acquiredT+0

    The task moves to a new QA Gate stage. The control plane enqueues the run and takes the lock on Legacy Maker Meats' staging instance. Nobody else's run can touch it until this one finishes, and the dashboard shows who holds the lock.

  3. Pre-flight auditT+40s

    The runner calls audit() over RPC. The sentinel is present and names the right client. Database name matches *_staging. Payment providers in test mode. But two ir.cron records are active, re-enabled during a hosting platform update three weeks ago.

    Verdict instance unsafe. The run stops before touching anything, the lead is alerted with the exact failed check, and the task does not move. Somebody disables the crons, and the run is retried. This is the system working correctly, and in the first month it will happen more often than you expect.

  4. Blast radius computedT+1m

    Diff parsed. Signals: a stored compute carcass_weight_kg on mrp.production with @api.depends on the pounds field, a write override with super() present, one QWeb template edit on the kill sheet, one new row in ir.model.access.csv for a new group_production_manager.

    Selected: 9 tier 1 probes, 71 tier 2 scenarios, 5 tier 3 flows, 4 personas because of the ACL row. Two static findings raised before anything runs: the stored compute has no migration script to populate existing rows, and the manifest declares no integration stub for a module that imports requests.

    There is no migration script in the diff, which is itself the first finding. Had there been one, the gate would have read it and reported on it rather than run it: there is one database, and executing a migration against it is the one-way change being tested. The bundle says that plainly instead of implying a confidence it does not have.

  5. Test plan posted, and held for approvalT+2m

    The interpretation, a seven-step workflow, ten test steps with provenance tags, and two ambiguities go to the task as a chatter note. Because the plan contains an AMB entry, the auto rule holds the run rather than proceeding.

    The lead reads it and confirms that the 2 percent threshold means 2 percent of the pounds value, then approves. Under two minutes of human time, and it stops steps T04 to T06 from testing the wrong number for the next three weeks. Section 11 shows this plan in full.

  6. Branch deployed to stagingT+4m

    Over the shell capability: fetch the branch, checkout, upgrade the module, restart. Two minutes and change. On a client without shell this step goes through the hosting panel's deploy mechanism instead, which is the one genuinely awkward part of the design and the one most worth automating per host.

    A fingerprint is taken immediately after the upgrade and compared to last night's baseline. The module hash differs only by the module under test, everything else matches, so the comparison stands.

  7. Tier 1, read-only probesT+5m

    Every view inheriting the MO form resolves and validates. The kill sheet renders for 5 sampled real manufacturing orders with no traceback, the kg column present, page count unchanged. And the NULL sweep confirms what the static analysis predicted: 4,182 existing MOs have an empty carcass_weight_kg, because there is no migration. Reported with the exact count, which is far more persuasive than a warning about a missing file.

  8. Tier 2, the regression suiteT+11m

    71 scenarios across 4 personas, each one a single run_scenario call executed and rolled back. Two failures.

    The first is the one that matters: mrp.unbuild_finished_order passed at baseline and fails at head with ValueError: Expected singleton, raised from the new write override which assumed a single record. That is a regression, and it is exactly what a developer clicking the happy path on staging would never hit.

    The second, account.tax_rounding_multi_line, also failed at baseline. pre-existing, filed to the backlog, does not block this task.

    Guard events: one scenario attempted an outbound HTTP call to the QuickBooks connector's endpoint. Blocked, and reported as a finding, since that module had no stub registered.

  9. Persona matrixT+13m

    Still tier 2, so still reversible. The ACL row is validated by replaying the MO confirm flow as each persona. A stock user is correctly blocked from approving a 2 percent variance. But a quality user, never mentioned in the task, is now also blocked from a screen they previously used, because the new ACL row narrowed write access on the model rather than adding a rule alongside it. Reported with the exact persona and screen.

  10. A developer needs staging, so the run pausesT+14m · held 38m

    Another developer clicks I need staging on the client's page rather than trying to find out who started the run. The request queues, and the run pauses at the next checkpoint 3 seconds later, mid tier 2, with 44 of 71 scenarios complete. Mode release, so the task branch stays deployed and the instance is usable immediately.

    Thirty-eight minutes later the requester marks themselves done and the run resumes. The pre-flight audit passes again, head is still the deployed commit, and the fingerprint has moved only in row counts and within tolerance, so all 44 completed scenarios are kept and execution picks up at number 45. Timings below are run time and exclude the pause.

  11. Tier 3, evidenceT+19m

    5 flows in Chromium against the real staging URL, 23 ordered screenshots, every field entry captured with the value typed and the value read back after save. Every record created is logged in the registry, and a write to any record not in the registry would have aborted the flow.

    Cleanup runs in reverse: the QA products and MOs unlink cleanly, one posted journal entry is reversed and both entries reported as residue, three sequence values consumed. All five rows appear in residue.json and in the report.

  12. Bundle and verdictT+21m

    Verdict regression, computed deterministically. The AI writes the summary paragraph. The lock releases. The task moves back to In Progress assigned to the developer, with the regression diff, the 4,182-row NULL count, the quality-user finding, and the unstubbed integration all in chatter. Screenshots are kept despite the failure, because the developer needs them to see what the change did do.

  13. Fix and re-runnext morning, T+13m

    The developer fixes the singleton assumption, adds the migration script, widens the ACL rather than narrowing it, and registers a stub for the connector. The re-run reuses the same baseline, which is still fingerprint-valid, and runs the identical selection. Verdict pass, task moves to PM Review with a 23-screenshot walkthrough and a residue table showing two reversal entries and nothing else.

    The project manager reads one paragraph and six screenshots instead of clicking through staging for 40 minutes. The mrp.unbuild scenario that caught the regression is now permanently part of Legacy Maker Meats' suite and will guard that path for every future task.

The last sentence is the compounding return. The gate's value on task one is a screenshot bundle. Its value on task fifty is a suite that has caught nine regressions nobody would have found before a client did.

Deploying a branch to a client staging instance has no universal mechanism. SSH plus git pull plus a module upgrade works where there is shell access. Cloudpepper has its own panel. Three things to get right at merge time

  • Cache keys. The dashboard's rule is that no Odoo-derived data is cached without being keyed by uid, because two users legitimately see different answers. QA run records are not per-user, they are per-task, so they must not go through those caches. Keep them in their own tables with their own access check, or they will either leak or be needlessly re-fetched.
  • Instance credentials are a new class of secret. The gate holds an Odoo API key per client staging instance, which is not the same thing as the signed-in user's own credential. It belongs with the runner, not in the dashboard's per-user session store, and it should never be resolvable from a browser session. Worth deciding deliberately rather than by accident.
  • Branch. Development on hst-pmo-dashboard happens on staging and Railway auto-deploys main. The QA merge lands on staging and reaches production when staging is merged, like everything else.

Worth noting what the dashboard gains beyond a new page. It already reads projects and tasks from Odoo. Adding QA outcomes means the executive view can answer questions it cannot today: which client's codebase is actually stable, how often work bounces back, whether the module a client wants extended has any coverage at all, and now also which client staging instances are healthy. That is a genuinely better dashboard, not just an extra tab.

What it will not do, stated plainly

  • It cannot make tier 3 residue-free. A browser click commits, and Odoo will not let you delete a posted entry. The design bounds and reports residue rather than pretending to eliminate it, and anyone who needs zero residue on staging should read section 6 and choose the QA company option knowing what it costs.
  • It cannot test a module uninstall, verify a migration script by running it, or dry-run a version upgrade. All three needed a database that could be thrown away afterwards, and a managed host does not provide one. The gate reads those changes statically and reports what it can see, but a human with a backup does the actual work. This is the largest capability difference between revision 2 on paper and revision 3 in reality, and nobody should discover it mid-project.
  • It cannot judge whether a feature is a good idea, whether the UX is right, or whether an ambiguous acceptance criterion was interpreted the way the client meant. Human review does not go away. It gets cheaper and better targeted.
  • It cannot find a bug in a path nobody has described. Coverage is exactly the union of the flow library and the client's ratified scenarios. The honest framing is that it makes every bug found once a bug that can never reach a client twice.
  • It will not replace testing on the client's production instance for changes involving hardware, real payment terminals, real printers, or real device integrations.
  • It does not make the first month faster. The gate adds 15 to 20 minutes to a task's cycle and, early on, will occasionally be wrong. The return arrives when the suite has depth, which is around task thirty for a given client.

23Is it working?

Four numbers, tracked from the first advisory run so there is a real before and after rather than a feeling. Everything else is vanity.

THE ONE THAT MATTERS

Client-reported regressions per month

Bugs in existing functionality, reported by a client, per client per month. This is the number the gate exists to reduce. Start counting it now, before the build, or you will have nothing to compare against.

EFFICIENCY

Bounce rate from PM Review

Share of tasks a project manager sends back. Should fall, because the obvious failures are caught earlier. If it does not move, the gate is testing the wrong things.

TRUST

False-positive rate

Share of blocking verdicts a developer overturns as wrong. Must stay under about 5 percent. Above that, turn blocking off for that client and fix the suite. This is the number that decides whether the tool is used or resented.

SAFETY

Residue records per run, and audit pass rate

New in this revision, and the licence to keep running against client instances. Residue should trend toward zero as cleanup rules improve. Audit pass rate across instances should reach 100 percent and stay there.

One operational number sits alongside these rather than among them, because it measures the instance rather than the gate: the ratio of paused time to running time per client. It is how you find out that a client's single staging instance has become the bottleneck, which is a capacity conversation with the host rather than anything the gate can fix.

One softer signal is worth watching too: whether developers start running the gate voluntarily before they are asked to. That happens when it is faster than clicking through staging themselves, and it is the point at which the tool has actually landed.
